============================================================================================
1. RESUMEN
============================================================================================

Una aplicación web de una sola página (SPA) hecha con React y TypeScript, construida con
Vite, que se publica como archivos estáticos. No necesita servidor ni base de datos para
funcionar: el contenido viaja con la aplicación y el progreso se guarda en el navegador
(IndexedDB), con exportación e importación a un archivo para no perderlo.

El contenido vive en la carpeta content/, separado del código:
  - Lecciones en MDX (Markdown con componentes interactivos insertados donde hacen falta).
  - Preguntas, tarjetas, ejercicios, escenarios y glosario en YAML.
  - Diagramas en SVG dentro de la carpeta de cada lección.
Agregar una lección es agregar una carpeta con sus archivos: la aplicación la descubre
sola al compilar, sin tocar código.

Toda la lógica de los simuladores (terminal, red, subnetting, validadores, exámenes,
diagnóstico, repetición espaciada) va en módulos de TypeScript puro, separados de la
interfaz, para poder probarlos a fondo con pruebas automáticas y reutilizarlos.


============================================================================================
2. STACK ELEGIDO Y POR QUÉ
============================================================================================

Base
  - React + TypeScript (modo estricto). React tiene el mejor ecosistema para los
    componentes complejos que pide la carrera (editor de código, grafos arrastrables,
    arrastrar y soltar accesible) y TypeScript evita errores en motores con mucha lógica.
  - Vite. Arranque y recarga instantáneos, configuración mínima y una función clave:
    import.meta.glob, que permite descubrir automáticamente todos los archivos de
    content/ al compilar. Eso es lo que hace que agregar una lección no requiera código.
  - MDX (con @mdx-js/rollup). Quien escribe contenido usa Markdown normal y, cuando
    necesita, inserta un componente: <Terminal ejercicio="./ej-permisos.yaml" />.
  - React Router para la navegación.
  - Tailwind CSS con variables CSS para el tema claro y oscuro y el diseño adaptable.

Datos y estado
  - YAML para datos estructurados (es cómodo de escribir a mano y admite comentarios),
    validado con Zod: si un archivo tiene un error, la compilación dice qué archivo, qué
    campo y qué está mal.
  - Dexie (sobre IndexedDB) para el progreso: más espacio que localStorage, consultas
    ordenadas y un modelo de tablas igual al que tendrá la base de datos futura.
  - Zustand para el estado de la interfaz (pequeño, simple y sin ceremonia).

Componentes de terceros (todos con licencias abiertas: MIT, Apache 2.0, ISC o MPL 2.0)
  - CodeMirror 6: editor de archivos de configuración con marcas de error en línea.
  - React Flow (@xyflow/react): constructor de topologías y mapa de la carrera.
  - dnd-kit: arrastrar y soltar, con soporte táctil y de teclado.
  - MiniSearch: buscador de texto completo en el navegador, tolerante a errores de tipeo.
  - ts-fsrs: algoritmo FSRS de repetición espaciada (más preciso que el clásico SM-2).
  - Ajv: validación de YAML contra esquemas JSON oficiales (Compose, Kubernetes).
  - yaml (eemeli/yaml): lectura de YAML conservando números de línea para los errores.
  - Pyodide (Python compilado a WebAssembly) y sql.js (SQLite en WebAssembly) para las
    consolas de Python y SQL. Se cargan solo en las lecciones que las usan.
  - Mermaid para diagramas de secuencia y de flujo generados con código; el resto de los
    diagramas son SVG propios.

Herramientas de desarrollo
  - Vitest y Testing Library (pruebas unitarias), Playwright (pruebas de punta a punta;
    el entorno ya trae Chromium), ESLint y Prettier, y GitHub Actions para correr todo en
    cada cambio.

Las versiones exactas se fijan en package.json al comenzar la Etapa 2, usando las
versiones estables vigentes en ese momento.


============================================================================================
3. ALTERNATIVAS DESCARTADAS
============================================================================================

  - Next.js: su punto fuerte es el renderizado en servidor, que aquí no hace falta. Suma
    complejidad hoy y, cuando haya usuarios, conviene una API separada.
  - Astro: excelente para sitios de contenido, pero esta plataforma es sobre todo una
    aplicación: progreso, notas, repaso y exámenes se comparten entre todas las páginas, y
    con las "islas" de Astro ese estado compartido se vuelve incómodo.
  - Docusaurus o VitePress: pensados para documentación; habría que pelear contra ellos
    para tener exámenes, progreso y simuladores.
  - Moodle u Open edX: requieren servidor y base de datos desde el día uno, el contenido
    no queda como archivos simples en el repositorio y los simuladores a medida son
    difíciles de integrar.
  - Linux real dentro del navegador (emuladores x86 en WebAssembly): se evaluó para la
    terminal. Exige descargar decenas de MB, es lento en teléfonos y no permite guiar ni
    validar ejercicios paso a paso. Queda como posible componente opcional a futuro; la
    práctica con sistemas reales se hace en los laboratorios con máquinas virtuales.

reordenar carpetas no rompe el progreso guardado de nadie.

5.2 Banco de preguntas (preguntas.yaml)

  Cada lección tiene entre 8 y 15 preguntas. El mini test muestra entre 5 y 10 y el resto
  queda para exámenes y diagnóstico, que prefieren preguntas que el estudiante todavía no
  vio. Las opciones se mezclan en cada intento. Ejemplos de cada tipo:

  - id: p01
    tipo: opcion_multiple
    enunciado: ¿Qué componente guarda los datos aunque se apague el equipo?
    opciones:
      - texto: El SSD
        correcta: true
        explicacion: Es almacenamiento no volátil, conserva los datos sin energía.
      - texto: La RAM
        explicacion: Es volátil; al cortar la energía se pierde su contenido.
    dificultad: 1                    # 1 básica, 2 intermedia, 3 avanzada
    diagnostico: true                # puede usarse en el diagnóstico inicial
    etiquetas: [almacenamiento]

  - id: p02
    tipo: respuesta_multiple         # varias correctas; se explica cada opción
  - id: p03
    tipo: completar_comando
    enunciado: Mostrar las últimas 20 líneas de /var/log/messages.
    aceptadas: [tail -n 20 /var/log/messages]   # respuestas exactas (sin importar espacios)
    patrones: []                     # expresiones regulares que también valen
    simulador:                       # o: ejecutar la respuesta en la terminal simulada
      shell: bash                    #    (bash o powershell) y comparar el resultado,
      estado_inicial: { ... }        #    así valen todas las formas correctas
      comparar_con: tail -n 20 /var/log/messages
      verificar: []                  # verificaciones extra, como en los ejercicios
    errores_frecuentes:
      - { patron: "^cat ", explicacion: "cat muestra el archivo entero, no las últimas líneas." }
    explicacion: ...
  - id: p04
    tipo: ordenar_pasos
    pasos: [Encendido, POST, Firmware busca el gestor de arranque, Kernel, systemd]
  - id: p05
    tipo: interpretar_salida
    salida: |
      Filesystem      Size  Used Avail Use% Mounted on
      /dev/sda2        50G   50G     0 100% /
    opciones: [...]
  - id: p06
    tipo: encontrar_error
    lenguaje: nginx
    archivo: |
      server {
          listen 80
          server_name ejemplo.com;
      }
    lineas_con_error: [2]
    explicacion: Falta el punto y coma al final de la directiva listen.

5.3 Ejercicio de terminal (cualquier .yaml referenciado desde la lección)

  tipo: terminal
  shell: bash                        # bash | powershell | ios
  titulo: Carpeta compartida para Contabilidad
  estado_inicial:                    # cada shell tiene su formato (ver src/engines/*/schema.ts)
    distro: rocky                    # rocky | ubuntu (cambia dnf/apt, firewalld/ufw, rutas)
    usuarios:
      - { nombre: estudiante, sudo: true }
      - { nombre: ana }
    grupos:
      - { nombre: contabilidad, miembros: [ana] }
    archivos:
      /srv/notas.txt: { contenido: "...", modo: "0640", dueno: ana, grupo: contabilidad }
    servicios:
      nginx: { activo: false, habilitado: false, puertos: [80] }
  pasos:
    - consigna: Lograr que el grupo contabilidad pueda crear archivos en /srv/compartido
                y que esos archivos hereden el grupo.
      verificar:
        - { archivo: /srv/compartido, grupo: contabilidad, modo: "2770" }
      pistas: [Revisar chgrp y chmod., El bit SGID en directorios hace heredar el grupo.]
      solucion: [sudo mkdir /srv/compartido, sudo chgrp contabilidad /srv/compartido, sudo chmod 2770 /srv/compartido]
      explicacion: Se muestra al completar el paso.

  Verificaciones disponibles:
    bash        archivo (tipo, modo, dueño, grupo, contenido), usuario, grupo, servicio,
                paquete, proceso, salida_contiene, salida_regex, comando_usado,
                directorio_actual, usuario_actual
    powershell  archivo, servicio, proceso, caracteristica (roles de Windows Server),
                usuario_ad, grupo_ad, ou, salida_contiene, salida_regex, comando_usado
    ios         config_contiene, vlan, interfaz (modo, VLAN, apagada, IP), ruta, ping
                (entre equipos de la topología), guardado, salida_contiene, comando_usado

  El validador ejecuta la solución de referencia de cada paso y comprueba que cumpla sus
  verificaciones: un ejercicio sin solución posible no llega a publicarse.

5.4 Escenario de troubleshooting (caso-real.yaml o cualquier escenario)

  tipo: troubleshooting
  titulo: El servicio web no responde
  inicio: n1
  nodos:
    n1:
      situacion: Avisan que la intranet no carga. ¿Qué conviene revisar primero?
      opciones:
        - { texto: Ver el estado del servicio con systemctl, ir_a: n2, minutos: 2 }
        - { texto: Reiniciar el servidor, ir_a: n9, minutos: 10,
            consecuencia: Se cortó el servicio a toda la empresa sin conocer la causa. }
    n2:
      situacion: ...
      evidencia:                     # salidas de comandos y logs, como en un caso real
        - { titulo: systemctl status nginx, contenido: "..." }
      opciones: [...]
    fin_ok: { final: exito, resumen: Qué se aprendió y qué se debió revisar primero. }

  La plataforma suma el tiempo de cada decisión y al final muestra el camino óptimo.
  Si todas las opciones tienen 0 minutos, el escenario es de decisiones sin reloj (por
  ejemplo, dilemas éticos): no muestra tiempo y cada elección se presenta como "buena
  decisión" o "esta decisión no fue la mejor", con su consecuencia.

5.6 Validación automática del contenido (npm run validar)
  Corre antes de cada compilación y en cada cambio subido al repositorio. Falla si:
  - Algún archivo no cumple su esquema (indica archivo, línea y campo).
  - Una lección no tiene objetivos, tiempo estimado, al menos un diagrama, al menos un
    interactivo, errores comunes, resumen o entre 8 y 15 preguntas en su banco.
  - Alguna pregunta no explica todas sus opciones.
  - Hay referencias rotas (requisitos de módulos, términos del glosario, archivos SVG o
    ejercicios inexistentes, ids repetidos).
  - Aparece texto de relleno ("lorem ipsum", "contenido pendiente", TODO).
  - Un ejercicio de terminal no se puede resolver: el validador ejecuta la solución de
    referencia en el simulador y comprueba que cumple las verificaciones.
  - La solución de un ejercicio de configuración no pasa sus propias reglas, la de un
    ejercicio de vim no deja el archivo como piden sus verificaciones, o una topología
    menciona equipos o interfaces que no existen.
  - Un componente recibe sus datos en una propiedad equivocada (por ejemplo,
    <Troubleshooting ejercicio={...}> en lugar de escenario) o con una variable que no
    está importada.
  Además avisa (sin fallar) si la fecha de verificación de una lección tiene más de un
  año.

5.7 Estilo de las explicaciones (desde el cierre de la Etapa 3)
  Pedido del estudiante: explicaciones sencillas, con ejemplos cotidianos, y una
  dificultad que suba de a poco. Cada lección nueva sigue estas reglas:
  - Empieza con <AntesDeEmpezar> cuando usa conceptos de lecciones anteriores: dos o
    tres puntos breves, con la lección donde se vieron si conviene repasar.
  - Cada concepto nuevo se presenta primero con una situación cotidiana (una oficina,
    una llamada, una dirección postal, monedas) y recién después con el término técnico
    y el detalle. Cuando el ejemplo deja de servir, se dice en qué punto, para no
    enseñar una idea equivocada.
  - Los conceptos que suelen costar llevan un recuadro <EnSimple> con la misma idea
    dicha de otra forma.
  - Un concepto nuevo por vez, con práctica (interactivo, terminal o pregunta) antes de
    sumar el siguiente. Si una sección mezcla varios conceptos nuevos, se divide.
  - Los ejercicios y las preguntas van de lo más fácil a lo más difícil dentro de la
    lección. Los usos avanzados que solo se mencionan se marcan como "para más adelante"
    para que el estudiante sepa que no tiene que retenerlos todavía.
  - El rigor técnico no cambia: los ejemplos cotidianos acompañan a la explicación
    técnica, no la reemplazan.
  En el Nivel 0 se aplicaron a las lecciones más densas: firmware y arranque, memoria
  virtual, binario, hexadecimal y octal, lógica binaria y el mapa de una página web.


============================================================================================
6. MOTORES Y COMPONENTES INTERACTIVOS
============================================================================================

Cada interactivo tiene dos partes: un motor en src/engines (lógica pura con pruebas
automáticas) y un componente en src/interactive (la interfaz). Así, por ejemplo, la
terminal y el constructor de topologías comparten el mismo motor de red: un ping desde la
terminal y un ping en el diagrama dan exactamente el mismo resultado.

6.1 Terminal simulada (Linux, PowerShell y consola tipo Cisco IOS)

    y sticky), fechas, enlaces duros y simbólicos. Los permisos se aplican de verdad: si
    el estudiante no tiene permiso, recibe el mismo error que en un sistema real.
  - Intérprete de bash: comillas, escapes, variables, comodines, tuberías, redirecciones
    (>, >>, 2>, &>, <), &&, ||, ; y sustitución de comandos. Soporta scripts simples.
  - Comandos como módulos independientes con sus opciones más usadas y mensajes de error
    fieles a GNU coreutils. Subsistemas simulados: usuarios y grupos, sudo, procesos y
    señales, servicios de systemd con su journal, paquetes, discos y particiones, red.
  - PowerShell (formato de Windows PowerShell 5.1): intérprete propio con pipeline de
    objetos reales (Where-Object, Select-Object, Sort-Object, Group-Object,
    Measure-Object, Format-Table/List, Export/Import-Csv, ConvertTo-Json...), variables,
    hashtables, if/foreach/while, funciones y scripts .ps1 con política de ejecución.
    Módulos: archivos, servicios, procesos, eventos, red (Get-NetIPAddress,
    Test-NetConnection, Resolve-DnsName), usuarios y grupos locales, roles y
    características (Install-WindowsFeature) y ActiveDirectory (usuarios, grupos, OU,
    equipos, filtros -Filter y -LDAPFilter, contraseñas como SecureString). Los módulos
    DnsServer, DhcpServer y Hyper-V se suman con los módulos 3.4 y 3.5. El detalle del
    Nivel 3 está más abajo.
  - Consola tipo IOS: modos (usuario, privilegiado, configuración global, interfaz,

    guardado), enable secret, contraseñas tipo 7 y claves RSA para SSH. Comandos show:
    running-config, ip interface brief, vlan brief, interfaces trunk, ip route, ip ospf
    neighbor, ip protocols, cdp neighbors, arp, mac address-table, version. Conectada al
    motor de red: el ping desde la consola usa las mismas VLAN y rutas que el diagrama.

    bpdufilter y err-disabled), EtherChannel (channel-group con LACP, PAgP y on),

    contadores de coincidencias, deny implícito, ip access-group in/out, show

    (pasan por las ACL). En las soluciones de referencia, "@consola EQUIPO" cambia de
    equipo.

  - Procesos con PID fijos y realistas (systemd, sshd, la sesión), servicios que crean
    su proceso al arrancar con el usuario de sistema del paquete (nginx, mysql, postgres,

  - Datos e integridad: file reconoce ELF, PE, PDF, PNG, JPEG, ZIP y gzip; md5sum,
    sha1sum, sha256sum, sha384sum y sha512sum (con -c); base64 (-d); bytes, UTF-8 y
    finales de línea CRLF visibles con od, xxd, cat -A y file.
  - Red del lado del cliente: ip, ping, traceroute, dig, nslookup, host, curl y wget

    resolución, la conexión, el saludo TLS y el certificado en las URL https.

6.2 Subnetting
  - Calculadora IPv4 (red, broadcast, rango, máscara, wildcard, tipo de dirección, vista
    binaria y división en subredes) y calculadora IPv6 (forma completa y abreviada según
    RFC 5952, tipo, prefijo de red, EUI-64).
  - Generador de ejercicios al azar por tipo y dificultad (red, broadcast, rango, cantidad
    de hosts, máscara necesaria, VLSM, sumarización, wildcard, IPv6), modo contrarreloj y
    estadísticas. Se prueba contra una implementación de referencia con miles de casos.

  - Nivel 2: los ejercicios de IPv6 parten las direcciones largas en pantallas chicas.

6.3 Motor de red, constructor de topologías y simulador de paquetes
  - Equipos: PC, servidor, switch de capa 2 y 3, y router, cada uno con sus interfaces
    (con los nombres reales: FastEthernet0/1, GigabitEthernet0/0/0...).
  - Simula: VLAN de acceso y troncales (VLAN nativa, permitidas y negociación DTP),
    subinterfaces 802.1Q (router-on-a-stick), interfaces VLAN en switches de capa 3, ARP,
    enrutamiento con rutas conectadas, estáticas y OSPF (adyacencias por área y máscara,
    DR/BDR, interfaces pasivas, ruta por defecto). Cuando un ping falla, explica en
    lenguaje claro dónde y por qué (troncal que no permite la VLAN, puerto en la VLAN
    equivocada, interfaz apagada, falta de ruta, respuesta que no vuelve...).
  - Se suman con las lecciones que los usan: firewall y punto de acceso como equipos,
    ACL y NAT (Nivel 2) y reglas de firewall (Nivel 8).
  - Desde la Etapa 5b: Spanning Tree (elección de raíz por VLAN, costos, puertos
    bloqueados y tormentas si se apaga), EtherChannel, HSRP, ACL de IOS (evaluadas en
    cada salto, en el sentido correcto) y sondas TCP/UDP a un puerto (net.probe).
  - Un ping produce una traza salto por salto; el constructor la muestra sobre el diagrama
    y el simulador de paquetes la anima capa por capa (qué encabezados se agregan y
    quitan en cada equipo).
  - Interfaz: arrastrar equipos y cables, configurar con formularios o con la consola.
  - El simulador de paquetes muestra también mensajes ARP (solicitud, respuesta y ARP
    gratuito), que van dentro de la trama sin encabezado IP (Etapa 5a).

6.4 Diagramas interactivos
  - SVG con zonas clicables definidas en YAML; al tocar una parte se abre su explicación.

  - Si el dibujo es muy apaisado (ancho/alto de 1,8 o más), ocupa todo el ancho y la

6.5 Arrastrar y soltar
  - Ordenar pasos y emparejar conceptos, con mouse, pantalla táctil o teclado.

6.6 Troubleshooting "elige tu camino"
  - Máquina de estados que recorre el grafo del escenario, suma tiempo y consecuencias, y

6.7 Editor de configuración con validación
  - CodeMirror 6 con resaltado y errores en línea (línea, columna, mensaje y explicación).
  - Validadores hechos: nginx (analizador propio con tabla de directivas y contextos,
    mensajes como los de "nginx -t" pero explicados), docker compose (Compose
    Specification: opciones, puertos, restart, depends_on, volúmenes y redes declarados),

    Nivel 1: sudoers (como visudo, con advertencias de seguridad: NOPASSWD con ALL,
    editores y shells, comodines) y unidades de systemd .service y .timer (secciones y
    opciones mal escritas con sugerencia, opciones en la sección equivocada, varios
    ExecStart, rutas sin /, tiempos y fechas de OnCalendar, WantedBy sin .target). En
    la terminal, visudo, crontab -e y systemctl edit validan o procesan antes de guardar.

    relativos y el punto final, paréntesis del SOA, tipos de registro, NS sin dirección,

    coma faltante, llaves, opciones mal escritas con sugerencia, zonas sin type o sin

  - Cada ejercicio agrega sus propias reglas (por ejemplo, "debe escuchar en 443 con

6.8 Tarjetas de repaso

6.9 Componentes específicos

    conversor de bases, calculadora de unidades y transferencias, operaciones de bits
    (con red y broadcast) y pasos guiados (ver 5.5).
  - Hechos en la Etapa 4a (Nivel 1): simulador de vim (modos, movimientos, edición,
    deshacer, búsqueda, reemplazo y comandos de :) y calculadora de permisos.
  - Hechos en la Etapa 5a (Nivel 2), con su motor en src/engines/redes: calculadora de
    PoE (normas af, at y bt, presupuesto por clase y práctica de "¿alcanza?"),
    simulador de la tabla MAC de un switch (aprender, reenviar, inundar, descartar y
    vencer, con predicción antes de cada envío), clasificador de direcciones IPv4 (con
    las trampas de 172.x y 100.x), diseñador VLSM (revisa alineación, tamaño,
    solapamientos y espacio, con caso fijo o al azar y una solución de referencia) y
    tabla NAT/PAT (puertos que se cambian, redirección y CGNAT).
  - Hechos en la Etapa 5b (Nivel 2): simulador de Spanning Tree, cómo decide un router
    (prefijo más largo y distancia administrativa), convergencia de vector distancia
    contra estado de enlace, firewall con estado (¿pasa este paquete? y ordenar
    reglas), planificador de canales Wi-Fi y visor de capturas al estilo Wireshark
    (VisorCapturas): lista coloreada, filtros de visualización con la sintaxis de
    Wireshark (incluido != como desde la versión 3.6), detalle por capas, seguir la
    conversación TCP y ejercicios de tipo "captura" con tareas de filtro (vale
    cualquier filtro equivalente), de marcar un paquete y de pregunta. Los escenarios
    de tráfico (visita web, retransmisiones, MTU y DNS) viven en src/engines/captura y
    los usan también tcpdump y mtr.
  - Hechos en la Etapa 6a (Nivel 3): calculadora de licencias de Windows Server
    (núcleos, Standard contra Datacenter y punto de equilibrio en máquinas virtuales) y
    simulador de directivas de grupo (SimuladorGPO: vincular, bloquear, exigir y filtrar,
    con el resultado por persona), los dos sobre motores con pruebas.
  - Pendientes, con el nivel que los usa: simuladores de RAID, quórum y migración; consolas de Python
    (Pyodide, en un proceso aparte para no trabar la página) y SQL (sql.js); consolas
    simplificadas de PromQL, LogQL y KQL sobre datos de ejemplo; constructor de rack y calculadoras (UPS, disponibilidad, cron, costos).
  - Los componentes pesados se cargan solo cuando una lección los usa.


============================================================================================
7. EVALUACIONES, DIAGNÓSTICO Y SUFICIENCIA (REGLAS EXACTAS)
============================================================================================

7.1 Mini test de lección
  - Entre 5 y 10 preguntas del banco de la lección. Se completa la lección con 70% o más
    (vale el mejor intento). Se puede repetir; cada intento mezcla preguntas y opciones.

7.2 Examen del módulo
  - 20 preguntas por defecto (configurable en modulo.yaml), repartidas entre todas las
    lecciones en proporción a sus horas y con al menos una por lección. Se priorizan
    preguntas no vistas y se mezclan los tipos.
  - Si el estudiante ya completó todas las lecciones del módulo, se aprueba con 70%.
  - Si no las completó, el examen cuenta como examen de suficiencia y se aprueba con 85%. La
    plataforma lo avisa antes de empezar.

7.3 Módulo completado
  - Por cursada: lecciones completadas + examen con 70% o más + caso real resuelto +
    laboratorio marcado como hecho (con su lista de verificación).
  - Por suficiencia: examen con 85% o más. El laboratorio y el caso real quedan sugeridos.

7.4 Recomendaciones después de un examen
  - Se calcula el porcentaje de aciertos por lección dentro del examen. Las lecciones por
    debajo de 70% se recomiendan (no el módulo entero), con enlace directo a las secciones
    relacionadas con las preguntas falladas.

7.5 Diagnóstico inicial (opcional, se puede pausar y retomar)
  - Por nivel: 10 preguntas marcadas como aptas para diagnóstico, al menos una por
    módulo y el resto según las horas de cada módulo.
  - Corte: si en las primeras 5 preguntas de un nivel hay 4 errores, o si el nivel
    termina con menos de 40% de aciertos, el diagnóstico se detiene y los niveles
    siguientes quedan como "estudiar".
  - Marca por módulo: todas sus preguntas correctas = "dominado" (se sugiere el examen de
    suficiencia); 50% o más = "repasar"; menos de 50% = "estudiar".
  - El diagnóstico nunca da un módulo por aprobado.

7.6 Próximo paso recomendado (panel del estudiante)
  En este orden:
    1. Tarjetas de repaso vencidas, si hay.
    2. Lecciones recomendadas por exámenes fallados.
    3. Continuar el módulo en curso.
    4. Siguiente módulo en el orden de la carrera; si está "dominado", sugerir su examen de
       suficiencia; si le faltan requisitos, avisarlo.

7.7 Fortalezas y temas débiles
  - Se calculan por lección y por etiqueta a partir de todas las respuestas, dando más
    peso a las recientes y exigiendo un mínimo de 3 respuestas para opinar.

8. PROGRESO Y ALMACENAMIENTO
============================================================================================

8.1 Qué se guarda
  - Perfil: nombre visible y preferencias (tema, tamaño de letra, límite diario de
    tarjetas).
  - Progreso de lección: estado, mejor puntaje, intentos, tiempo activo y última visita.
  - Intentos de evaluación: tipo (mini test, examen, suficiencia, diagnóstico, simulacro),
    fecha, cada pregunta con su respuesta y si fue correcta, puntaje y resultado.
  - Estado de módulo: estado, marca del diagnóstico, laboratorio y caso real.
  - Notas personales por lección.
  - Estado de cada tarjeta de repaso (datos de FSRS).
  - Tiempo dedicado por día y por lección.
  - Insignias y certificados obtenidos.

8.2 Cómo se mide el tiempo
  - Solo cuenta el tiempo activo: pestaña visible y alguna interacción en los últimos 2
    minutos.

8.3 Repositorio de progreso
  - Toda la aplicación usa una única interfaz (ProgressRepository) con operaciones como
    guardar intento, leer progreso de módulo o actualizar nota. Hoy la implementa
    IndexedDB; mañana la implementará una API, sin cambiar el resto de la aplicación.
  - Los datos tienen número de versión y migraciones automáticas.
  - Exportar e importar el progreso a un archivo JSON desde Ajustes. La aplicación pide al
    navegador almacenamiento persistente para que no lo borre por falta de espacio.
  - Los intentos se guardan como eventos que no se modifican; eso simplifica la futura
    sincronización entre dispositivos.

8.4 Cuando haya usuarios y base de datos (fuera del alcance actual)
  - Una API separada (por ejemplo Node.js con Fastify) con PostgreSQL, con las mismas
    tablas que hoy tiene IndexedDB, e inicio de sesión con OpenID Connect.
  - Sincronización: el navegador sigue funcionando sin conexión y sube sus eventos cuando
    puede.
  - El contenido sigue siendo estático; solo el progreso pasa a la base de datos.
  - Certificados verificables con un código firmado (hoy los certificados son locales y
    no verificables por terceros, y así se aclara en el propio certificado).

9. FUNCIONES DE LA PLATAFORMA
============================================================================================

  - Mapa de la carrera: niveles y módulos como un mapa con conexiones de requisitos,

  - Panel del estudiante: próximo paso, progreso por nivel, tiempo dedicado (semana y

  - Buscador: índice generado al compilar con todo el texto de lecciones y glosario;
    cada resultado lleva a la sección exacta.
  - Glosario: lista alfabética con buscador; cada término enlaza a la lección donde se
    explica. Dentro de las lecciones, los términos muestran su definición al tocarlos.
  - Notas personales por lección, con una vista de todas las notas.
  - Tema claro y oscuro (sigue la preferencia del sistema y se puede cambiar a mano).
  - Diseño pensado primero para teléfonos.
  - Insignia y certificado por nivel, para descargar como PDF desde el navegador.
  - Modo simulacro de certificaciones (nivel 9).

11. CÓMO SE CORRE LOCALMENTE
============================================================================================

  Requisitos: Node.js 22 LTS o posterior y Git.

    git clone https://github.com/Gstar97/Sysadmin.git
    cd Sysadmin
    npm install
    npm run dev          -> abrir http://localhost:5173

  Otros comandos:
    npm run dev:demo     -> la plataforma con el contenido de prueba (una lección
                            completa, laboratorio, caso real, examen y proyecto)
    npm run build        -> valida el contenido, revisa tipos y genera dist/
    npm run preview      -> sirve dist/ localmente para probarla
    npm run validar      -> valida todo el contenido
    npm test             -> pruebas unitarias
    npm run test:e2e     -> pruebas de punta a punta (la primera vez:
                            npx playwright install chromium)
    npm run lint         -> revisión de estilo y errores comunes
    npm run typecheck    -> revisión de tipos

  La carpeta dist/ se puede publicar en cualquier servidor web (Nginx, Apache) o en
  servicios de páginas estáticas. Como la aplicación usa rutas del lado del navegador,
  el servidor tiene que devolver index.html para cualquier ruta que no sea un archivo
  (en Nginx: try_files $uri /index.html;).

12. RIESGOS Y CÓMO SE MITIGAN
============================================================================================

  - Alcance enorme: trabajo por etapas; el nivel 0 funciona como piloto y fija la calidad
    y el formato de todo lo que sigue.
  - Simuladores con menos funciones que un sistema real: cubren lo que se enseña en cada
    lección, avisan cuando algo no está soportado, y cada módulo tiene laboratorio en
    máquinas virtuales reales.
  - Contenido que envejece: fecha de verificación por lección, aviso automático a los 12
    meses y anexo de fuentes en el plan.
  - Tamaño de la aplicación: cada lección y cada componente pesado se cargan solo cuando
    se usan.
  - Pérdida del progreso local: exportación e importación, y pedido de almacenamiento
    persistente al navegador.
