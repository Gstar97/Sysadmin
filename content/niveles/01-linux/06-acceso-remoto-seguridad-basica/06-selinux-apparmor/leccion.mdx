"Le di permisos 777 y sigue diciendo Permission denied." Si trabajás con Rocky, vas a escuchar (o decir) esa frase. Casi siempre es **SELinux**, una capa de seguridad que va por encima de los permisos de archivos. Mucha gente lo apaga a la primera; un buen administrador aprende a leerlo, porque es de las protecciones más efectivas que tiene un servidor. Ubuntu tiene una capa parecida, **AppArmor**.

<AntesDeEmpezar>
- Permisos de archivos, dueños y grupos (lecciones 1.2.2 y 1.2.3).
- Servicios, registros y nginx sirviendo archivos (módulo 1.3).
- Puertos y firewall (lecciones 1.6.1 y 1.6.5).
</AntesDeEmpezar>

## Una segunda llave

Los permisos de siempre los decide el dueño de cada archivo: si el dueño le da permiso a otro, ese otro puede. SELinux agrega reglas que pone el sistema y que ni root salta a voluntad: cada programa solo puede hacer lo que su tipo tiene permitido. nginx, por ejemplo, puede leer contenido web y escuchar en puertos web, y nada más. Si alguien aprovecha una falla de nginx para meterse, queda encerrado en eso: no puede leer `/etc/shadow` ni los homes, aunque los permisos de esos archivos fueran abiertos.

Pensá en un hotel: tu tarjeta abre tu habitación (los permisos), pero además el sistema del edificio decide a qué pisos te lleva el ascensor según el tipo de tarjeta (SELinux). Una tarjeta de huésped no te lleva a la sala de máquinas aunque alguien haya dejado esa puerta abierta. Donde la comparación no llega: en SELinux, los "tipos de tarjeta" y los "tipos de puerta" son **etiquetas**, y casi todos los problemas vienen de una etiqueta equivocada.

## Modos y etiquetas

```bash
getenforce               # Enforcing, Permissive o Disabled
sestatus                 # el detalle
ls -Z /var/www/html      # la etiqueta de los archivos
ps -eZ | grep nginx      # la de los procesos (nginx corre como httpd_t)
```

- **Enforcing**: las reglas se aplican y las violaciones se registran. Así viene Rocky y así tiene que quedar.
- **Permissive**: no bloquea nada, solo registra. `sudo setenforce 0` lo pone así hasta el próximo reinicio: sirve para confirmar si un problema es de SELinux (si con permissive funciona, lo es), y se vuelve con `sudo setenforce 1`.
- **Disabled**: apagado. No lo hagas: volver a encenderlo después obliga a reetiquetar todo el disco.

Las etiquetas salen de reglas por ruta: todo lo que está en `/var/www` es `httpd_sys_content_t`, lo de un home es `user_home_t`, y así. Un archivo nuevo toma la etiqueta de la carpeta donde se crea. Y acá está la trampa más común: **`mv` conserva la etiqueta** (el archivo es el mismo, cambió de lugar) mientras que `cp` crea uno nuevo con la etiqueta del destino.

## Encontrar la denegación

Cuando SELinux bloquea algo, lo deja escrito en `/var/log/audit/audit.log`:

```bash
sudo ausearch -m avc -ts recent       # las denegaciones (AVC) de los últimos minutos
```

```text
type=AVC msg=audit(...): avc:  denied  { read } for  pid=1159 comm="nginx" name="index.html"
  scontext=system_u:system_r:httpd_t:s0 tcontext=unconfined_u:object_r:user_home_t:s0 tclass=file
```

Se lee así: el programa **nginx** (que corre como **httpd_t**) quiso **leer** un **archivo** con etiqueta **user_home_t**, y se le negó. `audit2why` (en el mismo paquete que semanage) explica la causa probable:

```bash
sudo ausearch -m avc -ts recent | audit2why
```

## Los tres arreglos de siempre

<Emparejar ejercicio={causas} />

**1. La etiqueta de un archivo.** Si está en un lugar estándar y tiene una etiqueta equivocada (porque se movió con mv), alcanza con `restorecon`, que vuelve a poner la que corresponde. Si es un lugar nuevo, primero se agrega la regla:

```bash
sudo semanage fcontext -a -t httpd_sys_content_t "/srv/catalogo(/.*)?"
sudo restorecon -Rv /srv/catalogo
```

La expresión `(/.*)?` hace que la regla valga para la carpeta y todo lo de adentro. `chcon -t` también cambia una etiqueta, pero es temporal: el próximo restorecon la deshace.

**2. La etiqueta de un puerto.** Un servicio en un puerto no estándar necesita que ese puerto tenga el tipo correcto:

```bash
sudo semanage port -l | grep http_port_t                 # los puertos web conocidos
sudo semanage port -a -t http_port_t -p tcp 8090          # nginx en el 8090
sudo semanage port -a -t ssh_port_t -p tcp 2222           # sshd en el 2222
```

**3. Un booleano.** Son interruptores para comportamientos opcionales:

```bash
getsebool -a | grep httpd                          # los de los servicios web
sudo setsebool -P httpd_can_network_connect on     # que nginx pueda conectarse a otra aplicación (proxy)
```

Sin `-P`, el cambio se pierde al reiniciar.

En Rocky, `semanage` y `audit2why` vienen en el paquete **policycoreutils-python-utils**, que muchas instalaciones mínimas no traen: `sudo dnf install policycoreutils-python-utils`.

<EnSimple>
Si algo falla con "Permission denied" y los permisos están bien, mirá `ausearch -m avc`. Casi siempre es una de tres cosas: la etiqueta de un archivo (restorecon, semanage fcontext), la de un puerto (semanage port) o un booleano (setsebool -P). Apagar SELinux no es un arreglo.
</EnSimple>

Para más adelante: `audit2allow` genera un módulo de política a partir de las denegaciones. Es una herramienta potente y peligrosa: si la usás antes de entender la causa, le das permisos de más al programa. Casi nunca hace falta para los problemas de todos los días.

## AppArmor en Ubuntu

Ubuntu usa **AppArmor**, que persigue lo mismo con otro enfoque: en lugar de etiquetas, cada programa confinado tiene un **perfil** con las rutas que puede leer, escribir o ejecutar. Los perfiles están en `/etc/apparmor.d/` y cada uno está en modo **enforce** (bloquea) o **complain** (solo registra).

```bash
sudo aa-status                          # perfiles cargados y en qué modo
sudo journalctl -k | grep DENIED        # denegaciones: apparmor="DENIED" operation="open" profile="..."
```

En un Ubuntu Server recién instalado, AppArmor confina algunos servicios (chronyd, rsyslogd, tcpdump, y los que traen sus paquetes, como MySQL), pero no nginx. El problema típico aparece cuando movés los datos de un servicio confinado a otra carpeta (por ejemplo, los de MySQL): el perfil no conoce la ruta nueva y se agrega en `/etc/apparmor.d/local/`. Para probar, `sudo aa-complain PERFIL` (del paquete apparmor-utils) lo pasa a modo que solo registra; después se vuelve con `aa-enforce`.

<Resumen>
- SELinux (Rocky) y AppArmor (Ubuntu) limitan lo que puede hacer cada programa, aunque los permisos lo permitan.
- Modos: enforcing (así queda), permissive (`setenforce 0`, solo para diagnosticar), disabled (no).
- Etiquetas: `ls -Z`, `ps -eZ`. Importa el tipo. `mv` conserva la etiqueta; `cp` toma la del destino.
- Diagnóstico: `sudo ausearch -m avc -ts recent` (y `audit2why`).
- Arreglos: archivo → `restorecon -Rv` (+ `semanage fcontext -a -t TIPO "RUTA(/.*)?"`); puerto → `semanage port -a`; booleano → `setsebool -P`.
- AppArmor: perfiles por programa en `/etc/apparmor.d/`, `aa-status`, denegaciones con `apparmor="DENIED"` en el registro del kernel.
</Resumen>
