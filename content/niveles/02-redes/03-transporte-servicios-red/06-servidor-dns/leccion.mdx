En la lección 3 aprendiste a preguntarle al DNS. Ahora vas a ser el DNS. Toda empresa necesita, como mínimo, dos cosas: un **resolvedor** para que sus equipos naveguen (y que no dependa de un servicio de afuera), y un **autoritativo** para sus nombres internos (`intranet`, `ns1`, `impresora-2piso`). En Linux, los programas estándar son **BIND** (autoritativo, y también puede resolver) y **Unbound** (resolvedor). Esta lección los arma por separado y los conecta.

## La arquitectura

Piensa en la recepción de una empresa grande. Una persona en la entrada (el resolvedor) atiende todas las preguntas de los empleados: si es sobre un área interna, llama al conmutador interno (el autoritativo); si es de afuera, averigua por su cuenta. Y anota las respuestas en una libreta para no volver a averiguar lo mismo (la caché). Donde la comparación no llega: el resolvedor solo le debe responder a la gente de adentro; uno que responde a cualquiera de internet (un "resolvedor abierto") se usa para ataques de amplificación contra terceros.

<Diagrama svg={arquitectura} alt="Los equipos de la red le preguntan todo a Unbound (resolvedor en 192.168.10.53, con caché, solo para la red interna). Unbound reenvía las consultas de empresa.internal a BIND (autoritativo en 192.168.10.54, con la zona directa y la inversa, sin recursión) y resuelve todo lo demás en internet." pie="Resolvedor para todos; autoritativo solo para la zona interna." />

<Nota titulo="¿Por qué empresa.internal y no empresa.local?">
`.local` está reservado para mDNS (lo usan las impresoras y los equipos de Apple para encontrarse sin servidor) y usarlo en un DNS normal genera conflictos. Para nombres internos, lo recomendado hoy es un subdominio de un dominio propio (`corp.empresa.com`) o el dominio `.internal`, que ICANN reservó en 2024 justamente para redes privadas.
</Nota>

## BIND: el autoritativo

En Rocky se instala con `sudo dnf install bind bind-utils` y el servicio se llama `named`; en Ubuntu, con `sudo apt install bind9` (el servicio también es `named`). Los archivos cambian de lugar:

<Distros>
  <Distro nombre="Rocky / Alma Linux 10">
    Configuración en `/etc/named.conf` (y `/etc/named.rfc1912.zones`). Las zonas, en `/var/named/`. Viene configurado para responder **solo** al propio servidor: `listen-on port 53 { 127.0.0.1; };` y `allow-query { localhost; };`.
  </Distro>
  <Distro nombre="Ubuntu 24.04">
    Configuración repartida en `/etc/bind/named.conf.options` (opciones) y `/etc/bind/named.conf.local` (tus zonas). Las zonas se suelen poner en `/etc/bind/` o `/var/lib/bind/`. Viene escuchando en todas las interfaces y con recursión solo para las redes locales.
  </Distro>
</Distros>

### El archivo de zona

Una zona es un archivo de texto con registros. Este es el de `empresa.internal`:

```text
$TTL 1h
@   IN  SOA ns1.empresa.internal. admin.empresa.internal. (
        2026110201 ; serial
        1h         ; refresh: cada cuánto un secundario busca cambios
        15m        ; retry: si falla, cuándo reintenta
        1w         ; expire: cuánto sigue respondiendo un secundario sin el primario
        5m )       ; TTL de las respuestas negativas (NXDOMAIN)
    IN  NS  ns1.empresa.internal.
    IN  MX  10 mail
ns1       IN  A     192.168.10.54
mail      IN  A     192.168.10.25
intranet  IN  A     192.168.10.80
www       IN  CNAME intranet
```

Las reglas que más errores evitan:

- **`@`** es el nombre de la zona; una línea que empieza con espacio usa el mismo nombre que la anterior.
- **Nombres relativos y completos**: `mail` se completa como `mail.empresa.internal.`; `ns1.empresa.internal.` **con punto final** es un nombre completo. Si te olvidas el punto, BIND le agrega la zona y queda `ns1.empresa.internal.empresa.internal.`.
- En el SOA, el correo del responsable se escribe con **punto en lugar de @**: `admin.empresa.internal.`.
- El **serial** se sube **cada vez** que cambias la zona. La convención es la fecha más un número de cambio: `2026110201`, `2026110202`... Los servidores secundarios solo copian la zona si el serial aumentó.

### Declarar la zona y probar

La zona se declara en la configuración (en Rocky, al final de `/etc/named.conf`; en Ubuntu, en `named.conf.local`):

```text
zone "empresa.internal" IN {
    type primary;
    file "db.empresa.internal";
};
```

Y antes de arrancar o recargar, **siempre** se valida:

```bash
sudo named-checkconf -z                # sintaxis y todas las zonas
named-checkzone empresa.internal /var/named/db.empresa.internal
sudo systemctl enable --now named
sudo rndc reload                       # aplicar cambios de zona sin reiniciar
dig @127.0.0.1 www.empresa.internal    # probar en el propio servidor
```

<Advertencia titulo="Editar no es aplicar">
named sigue sirviendo la zona que cargó al arrancar. Si editas el archivo y no haces `rndc reload` (o reinicias), los clientes siguen viendo lo viejo. Y si la zona nueva tiene un error, named la rechaza y sigue con la anterior: revisa siempre `journalctl -u named` después de recargar.
</Advertencia>

### La zona inversa

Para que `dig -x 192.168.10.80` devuelva `intranet.empresa.internal`, hace falta una **zona inversa**. Las IP se escriben al revés y se les agrega `in-addr.arpa`: la red `192.168.10.0/24` es la zona `10.168.192.in-addr.arpa`, y cada registro es un **PTR** con el último octeto:

```text
zone "10.168.192.in-addr.arpa" IN { type primary; file "db.192.168.10"; };
```

```text
$TTL 1h
@   IN  SOA ns1.empresa.internal. admin.empresa.internal. ( 2026110201 1h 15m 1w 5m )
    IN  NS  ns1.empresa.internal.
54  IN  PTR ns1.empresa.internal.
25  IN  PTR mail.empresa.internal.
80  IN  PTR intranet.empresa.internal.
```

Aquí el punto final es obligatorio en los nombres de los PTR: sin él quedarían como `intranet.empresa.internal.10.168.192.in-addr.arpa.`.

## Unbound: el resolvedor

Para el resolvedor de la red se usa Unbound: es liviano, rápido y valida DNSSEC por defecto. Su configuración está en `/etc/unbound/unbound.conf` (en Rocky se pueden agregar archivos en `/etc/unbound/conf.d/`; en Ubuntu, en `/etc/unbound/unbound.conf.d/`):

```text
server:
    interface: 0.0.0.0                       # por defecto escucha solo en 127.0.0.1
    access-control: 192.168.10.0/24 allow    # por defecto solo responde a localhost
    domain-insecure: "empresa.internal"      # la zona interna no está firmada con DNSSEC

forward-zone:
    name: "empresa.internal"
    forward-addr: 192.168.10.54              # lo interno se le pregunta a BIND

forward-zone:
    name: "10.168.192.in-addr.arpa"
    forward-addr: 192.168.10.54              # y la inversa también
```

Para todo lo demás, Unbound recorre el árbol desde la raíz por su cuenta. Si la empresa prefiere pasar todo por un resolvedor externo (por ejemplo, uno que filtra sitios peligrosos), se agrega un `forward-zone` con `name: "."`.

```bash
sudo unbound-checkconf                   # revisar la configuración
sudo systemctl enable --now unbound
dig @127.0.0.1 www.empresa.internal      # lo interno, a través de BIND
dig @127.0.0.1 rockylinux.org            # lo externo
```

Por último, el DHCP les entrega a los equipos la IP de Unbound como servidor DNS (lección siguiente), y queda todo conectado. Vas a armar la arquitectura completa en el laboratorio.

<EnSimple>
BIND guarda los nombres de la empresa. Unbound es el que contesta las preguntas de todos los equipos: lo de la empresa se lo pregunta a BIND, lo demás lo busca en internet, y todo lo guarda un rato para contestar más rápido.
</EnSimple>

<ErroresComunes>
  <ErrorComun titulo="Olvidar el punto final en un nombre completo">
    NS, MX, CNAME y PTR que apuntan a nombres completos llevan punto al final. Sin él, BIND les agrega la zona. named-checkzone lo detecta cuando el NS queda sin dirección.
  </ErrorComun>
  <ErrorComun titulo="Cambiar la zona y no subir el serial">
    El primario sirve el cambio después del reload, pero los secundarios no lo copian y responden con datos viejos. Súbelo en cada cambio.
  </ErrorComun>
  <ErrorComun titulo="El servidor responde en sí mismo pero no a la red">
    En Rocky, named viene con listen-on 127.0.0.1 y allow-query localhost, y firewalld no deja pasar el 53. Revisa los tres: ss -ulnp (¿dónde escucha?), allow-query y firewall-cmd --list-services.
  </ErrorComun>
  <ErrorComun titulo="Un resolvedor abierto a internet">
    Un resolvedor que responde a cualquiera se usa en ataques de amplificación. Limita quién puede preguntar (allow-query o allow-recursion en BIND, access-control en Unbound) y no lo publiques hacia afuera.
  </ErrorComun>
  <ErrorComun titulo="Editar y no aplicar">
    Después de cambiar una zona: named-checkzone, sudo rndc reload y journalctl -u named para confirmar que cargó.
  </ErrorComun>
</ErroresComunes>

<Resumen>
- Arquitectura típica: Unbound como resolvedor para toda la red (con caché y solo para la red interna) y BIND como autoritativo de la zona interna, sin recursión.
- Zona: $TTL, SOA (servidor primario, correo con punto, serial, tiempos), NS y los registros. Nombres completos con punto final. Serial con fecha + número, subirlo en cada cambio.
- Declaración: zone "nombre" IN { type primary; file "archivo"; };. Validar con named-checkconf -z y named-checkzone; aplicar con rndc reload.
- Zona inversa: la red al revés + in-addr.arpa (10.168.192.in-addr.arpa), con registros PTR.
- Rocky trae named solo para localhost: listen-on, allow-query y firewall (servicio dns).
- Unbound: interface, access-control, forward-zone hacia BIND para la zona interna, domain-insecure si no está firmada. Validar con unbound-checkconf.
</Resumen>
