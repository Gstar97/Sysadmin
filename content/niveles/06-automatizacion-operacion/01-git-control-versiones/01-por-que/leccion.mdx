Hasta acá configuraste servidores a mano: editabas un archivo, probabas y, con suerte, guardabas una copia .bak antes. Funciona con un servidor y una persona. Con diez servidores, tres personas y un año de cambios, ya no: nadie sabe qué versión es la buena, por qué alguien cambió una línea, ni cuándo se rompió algo. Este nivel trata de dejar de hacer las cosas a mano, y el primer paso es guardar todo lo que configurás en un **sistema de control de versiones**. El que usa todo el mundo es **Git**.

## Qué es Git

- Un **repositorio** es una carpeta cuyo historial maneja Git. La historia vive en una carpeta oculta, `.git`; los archivos de afuera son archivos comunes que editás como siempre.
- Un **commit** es una foto de todos los archivos del repositorio en un momento, con el autor, la fecha y un mensaje. Cada commit tiene un identificador (como `a41c9e2`) y apunta al anterior: así se forma la historia.
- Git es **distribuido**: cada copia del repositorio tiene la historia completa. Se puede trabajar sin red y después sincronizar con un servidor central (GitHub, GitLab, Gitea o un servidor propio).

Git lo creó Linus Torvalds en 2005 para el kernel de Linux, y hoy es la herramienta común de desarrolladores y de administradores: las configuraciones, los scripts, los playbooks de Ansible del módulo 6.3, los paneles de monitoreo, la documentación. A todo eso se lo llama **infraestructura como código**, y su base es que lo que define cómo están los servidores vive en un repositorio.

## Lo que Git te da

- **Historia**: quién cambió qué, cuándo y por qué. `git log` y `git blame` (lección 6.1.5) responden "¿quién tocó esta línea?".
- **Diferencias**: `git diff` muestra exactamente qué cambió, antes de guardarlo y entre dos momentos cualesquiera.
- **Volver atrás**: cualquier archivo, a cualquier versión.
- **Trabajar en paralelo**: ramas para probar un cambio sin tocar lo que anda (lección 6.1.3).
- **Una sola fuente de verdad**: un repositorio central del que todos los servidores toman la configuración (lecciones 6.1.4 y 6.1.5).

Y lo que **no** te da: no es un respaldo de los servidores (solo guarda lo que pusiste en él) y no es lugar para contraseñas (cualquiera que lo clone las ve, y quedan en la historia para siempre: lo vas a ver en el caso del módulo).

<EnSimple>
Git guarda fotos de una carpeta, llamadas commits, cada una con quién la sacó, cuándo y un mensaje que explica qué cambió y por qué. Así deja de haber archivos .bak sin explicación: se ve toda la historia, qué cambió entre dos fotos, y se puede volver a cualquiera. La historia vive en la carpeta .git. Primero se le dice a Git quién sos (nombre y correo), después git init, git add y git commit. Git no reemplaza a los respaldos y no es lugar para contraseñas.
</EnSimple>

<Resumen>
- Control de versiones: la historia de cada cambio, con quién, cuándo, qué y por qué.
- Repositorio: la carpeta con su historia en .git. Commit: una foto con autor, fecha y mensaje.
- Git es distribuido: cada copia tiene la historia entera; se sincroniza con un servidor central.
- Una vez por equipo: git config --global user.name, user.email e init.defaultBranch main.
- git init, git status, git add, git commit -m, git diff, git log, git show COMMIT:archivo.
</Resumen>
